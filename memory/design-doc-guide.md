# 设计说明书撰写规范（v4 — 13份文档全量对比版）

**来源：** 对比全部 13 份设计说明书（6份已完成 + 7份待完成）提炼。

**Why:** 用户需要为软著申请频繁撰写设计说明书，此规范包含从实际文档中提炼的章节结构、第一章写法模板、模块写法模板、格式参数，保证每次生成的文档质量统一。
**How to apply:** 每次撰写设计说明书时，必须读取此规范，严格按参数生成。

**⚠️ 红线：开始撰写前必须先确认系统正式全称（含 Neowow 前缀），后续所有文档、插图中必须使用完全一致的名称，不得省略、不得前后不一致。插图标题中的系统名称必须与正文完全一致。**

## 三-B、第一章写法模板（版本 A — 设计概述式）

### 1.1 软件用途与运行形态 — 5段式结构

**第1段：系统定位**
```
{系统全称}（以下简称本系统）是一款面向 Neowow 内容生产工具平台的
{系统类型}软件，参考{设计理念}的设计理念构建。
```

**第2段：核心价值**
```
本系统的核心价值在于{解决什么问题}。传统工作流中{痛点描述}。
本系统通过{功能1}、{功能2}、{功能3}等功能，{达成的效果}。
```

**第3段：运行形态**
```
本系统以 Web 应用形态运行：对外提供标准 REST 接口（统一前缀/api/v1/），
以 JWT Token 的方式鉴权。系统所有数据模型均自主定义，不依赖外部系统的
存量数据表，接入方只需按接口协议调用即可获得完整{X}管理能力，具备
低侵入、可独立部署的特点。
```

**第4段：分层架构**
```
系统采用分层架构设计，由{展示层}、{API层}、{业务层}、{数据层}和{AI层}
{N}层构成。各层通过标准化接口交互，松耦合，可独立部署和扩展。
```

**第5段：开发目标 + 部署方式**
```
本系统的开发目标包括：第一，{目标1}；第二，{目标2}；第三，{目标3}。
系统预期用户规模：初期支持{N}并发用户，后期可扩展至{N}并发用户。
部署方式：系统支持 Docker 容器化部署...
```

### 1.2 功能总览 — 必须有3列表格

```
本系统包含{N}大功能模块，各模块功能概述如下：
```

| 序号 | 功能模块 | 功能概述 |
|------|----------|----------|
| 1 | {模块名} | 输入为{X}；处理为{Y}；输出为{Z}。{技术特点描述}。 |

**每个模块的功能概述要包含：输入→处理→输出 + 技术特点。**

### 1.3 运行环境
```
开发与运行的硬件环境：CPU 2GHz 或以上；内存 8G 或以上；硬盘 200G 或以上。
操作系统：Windows Server 2016 及以上或主流 Linux 发行版（CentOS 7+/Ubuntu 20.04+）。
运行支撑环境：JDK 17 及以上、MySQL 8.0 及以上、Redis 7.x 及以上、Nginx 1.20 及以上。
开发工具：IntelliJ IDEA、Maven、Git。工程基于 Spring Boot 3.2 与 MyBatis-Plus 构建。
```

**⚠️ 不要有 1.5 参考资料 / 参考文献 小节。**

## 五、图表规范（v3 — 含用户确认的图表设计标准）

### ️ 核心要求

**图必须是程序绘制的 PNG 插入，禁止 ASCII 字符画。**

### 图表类型与最低数量

| 图表类型 | 最低数量 | 放置章节 |
|----------|----------|----------|
| 系统功能结构图 | ≥1 张 | 1.2 功能总览 |
| 系统逻辑架构图 | ≥1 张 | 4.1 系统架构设计 |
| 模块关系图 | ≥1 张 | 4.1 或 4.2 |
| 功能流程图 | 每模块 ≥1 张 | 5.x 各模块内 |
| E-R关系图 | ≥1 张 | 3.2 E-R图 |
| **总计** | **≥7 张** | |

### 图表在文档中的格式要求

1. **每张图前后必须有文字说明**
2. **图下方居中写图号图名**：`图 X.X 图名`（12pt 居中）
3. **图号全文连续递增**：图1.1、图3.1、图4.1、图4.2、图5.1...
4. **图片尺寸**：宽约 6.0 英寸（≈15cm），分辨率 200 DPI
5. **图片居中放置**

### 图表依赖
- `matplotlib` — 图表绘制
- `Pillow` — 图片处理
- 中文字体：`SimHei`（Windows 黑体）

### 系统逻辑架构图设计规范（v3 已确认 ✅）

**用户确认的最终方案，以后严格按此执行：**

1. **四层结构**：接入层（API网关）→ 业务层（功能模块）→ 数据访问层（过渡条）→ 数据层（存储组件）
2. **关键技巧：加数据访问层过渡条** — 业务模块和数据存储之间加横跨整图的灰色圆角条，彻底消除交叉箭头
3. **所有箭头垂直直线** — 零交叉零斜线
4. **方框大小必须与文字内容匹配** — ⚠️ 绝不允许文字少框子大！根据文字长度动态调整框宽，保证文字至少占框宽 50% 以上
5. **箭头不戳进方框** — `edge()` 函数算边缘交点 + 0.12 间距
6. **左侧层标签** — 竖排文字标注各层名称
7. **图标题**：`系统逻辑架构图` 16pt 加粗 居中

### E-R 关系图设计规范（v3 已确认 ✅）

1. **方框统一尺寸**（2.8 × 1.2）
2. **箭头不戳进方框** — 射线与矩形边缘交点 + 0.15 间距
3. **标签不遮挡** — 关系标签带白色圆角背景
4. **所有方框必须连通** — 不能有孤立方框
5. **对称布局** — 3×2 网格
6. **底部注释** — italic 说明核心表和关联关系

### 流程图设计规范

1. **动态图高** — 根据步骤数自动计算：`图高 = 步骤数×框高 + 间距 + 上下边距`
2. **框宽匹配文字** — ≤8字用2.6宽，≤14字用3.4，超长用3.8
3. **箭头垂直直线** — 从上框底到下框顶，留 0.12 间距
4. **上下边距各 1.0 英寸** — 保证首尾框完整不被裁切
5. **配色**：普通步骤淡蓝 `#E4EEF7`+蓝边框，特殊步骤淡黄 `#FFF8E1`+金边框，完成步骤淡绿 `#E8F5E9`+绿边框

## 六、编写原则

- **先整体后局部**：先写概要设计，再细化详细设计
- **图文并茂**：架构图、流程图、E-R图必须为 PNG 真图（但已完成的待完成文档中也有用 ASCII 字符画架构图的，v4 仍以 PNG 为准）
- **保持一致性**：术语、命名、格式在整个文档中统一
- **可追溯性**：每个设计决策能追溯到对应的需求
- **面向读者**：假设读者不了解你的思路，要解释清楚每个决策
- **前端内容控制** — 前端相关内容控制在总篇幅的 10% 以内，侧重后端业务逻辑描述
- **删多少补多少** — 删减内容时必须用其他章节扩写补齐，净增长 ≥ 0
- **不提具体厂商名** — 禁止出现 OpenAI、通义千问、Claude、GPT、Anthropic、Midjourney、Stable Diffusion 等具体厂商/产品名称。用"多种主流大语言模型""一种图像生成模型"等通用表述替代。源代码中的配置键、变量名、依赖名同理（用 primary/secondary/tertiary 代替 openai/qwen/claude）
- **与平台关系的表述（v4 更新）** — 允许且应当说明系统是平台的子系统（这是实际情况）：
  - ✅ "是 Neowow 内容生产工具平台的{X}子系统"
  - ✅ "面向 Neowow 内容生产工具平台"
  - ✅ "对接 Neowow 用户体系，实现统一身份认证"
  - ✅ "本系统以 API 服务形式运行，接入方是{平台名称}"
  - ✅ "对上屏蔽{X}的对接细节，对下保证{Y}"
  - ❌ "嵌入XX平台运行"（暗示没有独立性）
  - ❌ "复用XX平台"（暗示没有自己的逻辑）
