# 软著源代码文档生成技能

当用户需要为软著登记生成源代码文档时触发。

## 触发条件

- 用户说"帮我写源代码文档"、"生成软著代码"
- 用户说"提取源代码"、"整理代码提交"
- 用户通过 `/generate-source-code-doc` 命令触发
- 被 `copyright-workflow` 全流程调用

## 执行流程

### Step 1：确认输出路径与目录

**优先使用 `collect-info` 已确认的输出路径。** 如果未收集，则使用 AskUserQuestion 让用户指定。

检查 `result\` 目录是否存在：
- 不存在 → 创建 `result\`
- 已存在 → 直接使用
- 用户自建的其他目录 → 不碰

### Step 2：确认信息

**优先使用 `collect-info` 已收集的信息。** 如果未收集，则询问：

**使用 AskUserQuestion 提供选择题，每个问题必须包含：预设选项 + 跳过 + 自定义输入。**

| 信息 | 说明 |
|------|------|
| 软件全称 | 与申请表完全一致 |
| 版本号 | 与申请表完全一致 |
| 项目路径 | 源代码所在目录 |
| 编程语言 | 主要语言 |

### Step 3：代码提取

**扫描与过滤：**
```
1. 列出项目所有源代码文件
2. 排除：node_modules/venv/__pycache__/.git、第三方库、自动生成代码、敏感配置
```

**提取优先级（高→低）：**
1. 核心业务逻辑（models, services, controllers）
2. API路由与接口定义
3. 配置文件
4. 工具函数与中间件
5. 前端页面组件（必要时）

**提取规则：**
- 单文件最多取80行，超过时按函数/类边界截断
- 不足30行的文件可整体提取
- 文件之间用 `// ===== 文件名 =====` 分隔
- 保持原始缩进（Python尤其重要）

**禁止包含：**
- 第三方库代码
- 重复代码（同一工具函数只提取一次）
- 纯生成文件（migrations、编译产物、lock文件）
- CREATE TABLE 等 DDL 语句（只允许 DML）

### Step 4：生成 Word 文档

**排版规范：**
| 项目 | 设置 |
|------|------|
| 代码字体 | Consolas（唯一允许非宋体的地方） |
| 字号 | 10pt |
| 行距 | 固定值14磅 |
| 页边距 | 上2.0cm/下2.0cm/左2.5cm/右2.0cm |
| 页眉 | 软件名称 + 版本号，**宋体**9pt |
| 页脚 | 页码居中，**宋体**9pt |
| 段前段后 | 0 |

**页数控制：**
- 目标60页（前30页 + 后30页）
- 每页约50行，总目标约3000行
- 代码不足时扩大文件范围，优先补充业务模块

### Step 5：CMMI3 审查

生成后**自动调用 `cmmi3-review`** 审查：
- 总行数 ≥ 3000 行？
- 前后各30页连续？
- 每页 ≥ 50 行有效代码？
- 页眉信息与申请表一致？
- 代码功能是否与说明书对应？

审查不通过 → 自动修正 → 重新审查

### Step 5.5：格式自校验

生成后**必须用 python-docx 打开文档自动检查**：

- [ ] **页眉页脚字体**：页眉页脚 run 字体 = 宋体，字号 = 114300（9pt）
- [ ] **代码字体**：正文段落 run 字体 = Consolas，字号 = 127000（10pt）
- [ ] **页眉内容**：包含软件全称和版本号

修正方法：遍历页眉/页脚的所有 run，强制设置 `font.name = '宋体'` + `font.size = Pt(9)` + `_element.rPr.rFonts.set(qn('w:eastAsia'), '宋体')`。

### Step 6：保存文件

**保存位置：** `result\` 目录（在 `collect-info` 确认的输出路径下）

**命名格式：** `{软件全称}V{版本号}-源代码文档.docx`

### 异色字体标注规范（每个生成步骤后必须执行）

**核心原则：AI 自己补全/生成的内容标色，用户明确提供的不标。**

**判断规则：**
1. 用户通过 AskUserQuestion **明确选择了某个选项**的内容 → 黑色（不标色）
2. 用户选择"跳过"，由 **AI 自主决定**的内容 → 按风险等级标色
3. `ai_decisions` 列表存在时，**优先使用列表中的风险等级**；不存在时，AI **自主评估风险**

**风险自评标准：**
- **低风险（蓝色）**：文件分隔注释、代码注释
- **中风险（橙色）**：AI 补充的代码文件选择（选哪些文件、截断到哪个函数）
- **高风险（红色）**：AI 完全自生成的代码（用户项目中不存在但为凑页数编写的代码）

**python-docx 实现：**
```python
from docx.shared import RGBColor

def mark_risk(run, risk_level):
    colors = {
        'low':    RGBColor(0x2E, 0x86, 0xC1),  # 蓝色
        'medium': RGBColor(0xE6, 0x95, 0x2A),  # 橙色
        'high':   RGBColor(0xC0, 0x39, 0x2B),  # 红色
    }
    run.font.color.rgb = colors.get(risk_level, RGBColor(0, 0, 0))
```

**执行时机：** 在写入代码段落时，对 AI 代决策的部分 run 立即设置颜色。不要等生成完再批量修改。

## 行为约束

### 必须做到
- ✅ 代码功能需与说明书对应匹配
- ✅ 两个软著之间代码不能重复
- ✅ 生成后自动调用 cmmi3-review
- ✅ AI 代决策内容必须按风险等级异色标注（蓝/橙/红），用户明确提供的不标色

### 禁止做到
- ❌ 包含 CREATE TABLE 等 DDL 语句
- ❌ 包含第三方库代码
- ❌ 包含敏感配置（密码、密钥）
